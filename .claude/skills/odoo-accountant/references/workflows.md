# المسارات الستة — الخطوات

كل الاستعلامات قراءة فقط. `S` = بداية الفترة. الاستدعاء: `POST $ODOO_URL/json/2/<model>/<method>` برأس `X-Odoo-Database`.
نمط التجميع: `formatted_read_group` مع `domain` و`groupby` و`aggregates` (مثل `["__count","amount_total:sum"]`).
ملاحظة Odoo 19: الحقول غير المخزنة (مثل `edi_error_count`, `l10n_sa_show_reason`) لا تصلح للتجميع أو التصفية.

## 1) accounting-snapshot
- **متى:** طلب ملخص/حالة محاسبية.
- **المدخلات:** الفترة (افتراضي 90 يومًا)، شركة/فرع اختياري.
- **القراءة:**
  1. `account.move` مجمعًا حسب `move_type, state` (count, `amount_total:sum`) بمحور `date`.
  2. الفواتير (`out_invoice`,`in_invoice`) حسب `payment_state, state` مع `amount_residual:sum`.
  3. حسب `journal_id` و`currency_id` وشهر `invoice_date:month`.
  4. المتأخر: `state=posted` و`payment_state in (not_paid,partial)` و`invoice_date_due < اليوم`.
  5. `account.payment` (count/amount حسب state) و`account.bank.statement.line` حسب `is_reconciled`.
- **الكتابة:** لا شيء.
- **المخرج:** جدول موجز + تنبيهات (مسودات، متأخرات، غير مطابق).
- **الحدود:** بلا أسماء أطراف إلا عند الطلب.

## 2) overdue-followup
- **متى:** متأخرات، تحصيل، سداد موردين.
- **المدخلات:** `out` (عملاء) أو `in` (موردين)، حد الأيام، حد أدنى للمبلغ.
- **القراءة:** تجميع حسب `partner_id` و`invoice_date_due:month` مع `amount_residual:sum` للفواتير المرحّلة غير المسددة؛ ثم عيّنة سجلات (`name, partner_id, invoice_date_due, amount_residual, currency_id`) للأكبر.
  قبل التوصية: افحص أسطر `asset_receivable` الدائنة غير المطابقة للشريك نفسه (قد تكون دفعة لم تُسوَّ).
- **يحتاج موافقة:** إرسال أي رسالة، إنشاء نشاط `mail.activity`، تعديل شروط الدفع.
- **المخرج:** جدول أعمار (0-30/31-60/61-90/+90) وقائمة شركاء بالأولوية + مسودة نص رسالة (غير مرسلة).
- **الحدود:** لا إرسال، لا تعديل، لا تسوية.

## 3) bank-match-suggest
- **متى:** أسطر كشف بنكي غير مطابقة.
- **المدخلات:** اليومية/الفترة.
- **القراءة:** `account.bank.statement.line` بـ `is_reconciled=false` مجمعًا حسب `journal_id`؛ لكل سطر (عيّنة محدودة): `date, amount, payment_ref, partner_id`. ابحث عن فواتير مفتوحة (`amount_residual` = |amount|، نفس العملة، نفس الشريك إن وُجد، أو `ref`/الرقم في `payment_ref`).
- **القاعدة:** اقترح فقط عند تطابق مرشح **واحد** واضح؛ مع مرشحين أو أكثر أو بلا شريك يُعرض "غامض" دون اختيار.
- **يحتاج موافقة:** كل مطابقة فعلية، لكل دفعة/مجموعة صراحة.
- **المخرج:** جدول (سطر، مرشح/مرشحون، سبب، ثقة، غامض؟).
- **الحدود:** لا مطابقة تلقائية، لا إنشاء قيود فروقات، لا تغيير شريك السطر دون موافقة.

## 4) partner-data-quality
- **متى:** فحص نواقص الشركاء قبل الإرسال/الإقفال.
- **المدخلات:** الفترة، نوع (عميل/مورد).
- **القراءة:** عدّ فواتير الفترة حيث `partner_id.vat=false`؛ `partner_id.country_id=false`؛ أسطر بنكية بلا `partner_id`؛ موردون (`supplier_rank>0`) بلا `vat`. عيّنة محدودة بـ `id, name` فقط.
- **يحتاج موافقة:** أي تعديل على الشريك أو ربط سطر بشريك.
- **المخرج:** قائمة نواقص مرتبة بالأثر (عدد الفواتير/المبلغ).
- **الحدود:** لا اختراع رقم ضريبي؛ عميل فرد قد يكون بلا VAT طبيعيًا — اسأل ولا تحكم.

## 5) vendor-bill-review
- **متى:** فاتورة/مسودة مورد قبل الترحيل أو مراجعة دورية.
- **المدخلات:** أرقام الفواتير أو الفترة (`move_type=in_invoice`).
- **القراءة:** `account.move` (`name, partner_id, ref, invoice_date, invoice_date_due, state, payment_state, amount_total, currency_id, journal_id`) ثم `account.move.line` (`display_type=product`: `account_id, tax_ids, product_id, price_subtotal`).
- **الفحوص:** `ref` مفقود؛ بند بلا `product_id`؛ ضريبة غائبة أو غير متسقة مع المورد؛ حساب مصروف غير معتاد للمورد؛ تكرار محتمل (نفس المورد+المرجع+المبلغ)؛ مورد بلا VAT.
- **يحتاج موافقة:** أي تعديل، الترحيل، الدفع.
- **المخرج:** ملاحظات لكل فاتورة (سليمة / تحتاج مراجعة + السبب).
- **الحدود:** لا ترحيل ولا دفع، ولا تصحيح حساب/ضريبة بالتخمين.

## 6) period-close-check
- **متى:** قبل إقفال شهر/فترة.
- **المدخلات:** الشهر.
- **القراءة:** قيود `state=draft` حسب `journal_id` (خاصة الإهلاكات والعمليات المتنوعة)؛ فواتير مسودة؛ أسطر بنكية غير مطابقة؛ قيود دائنة غير مطابقة على العملاء؛ إجمالي المبيعات والضريبة؛ فواتير بلا تاريخ استحقاق أو شريك.
- **يحتاج موافقة:** ترحيل أي مسودة، قفل الفترة (`lock date`)، أي تسوية.
- **المخرج:** قائمة تحقق (✔ / ✘ + العدد والمبلغ) وتوصية "جاهز/غير جاهز".
- **الحدود:** قراءة فقط؛ القفل قرار المستخدم وحده.

## 7) statement-import (استيراد كشف بنكي)
- **متى:** المستخدم يقدّم كشفًا (CSV/XLSX أو صفوف جاهزة) للاستيراد.
- **المدخلات:** الملف أو `rows`، `profile`، وأربعة عناصر هدف صريحة (`company_id`, `journal_id`, `bank_account_id`, `currency`)، وأرصدة اختيارية.
- **الخطوات:** إن كان الملف XLS أو غير قياسي ← `normalize_statement_file` أولًا (راجع التقرير، وتوقف عند `needs_clarification`) ← `statement_import_preview` ← راجع الأعمدة والأرصدة والتكرار مع المستخدم ← `propose_statement_import` ← موافقة بالكود والبصمة ← `execute_approved_action` ← قراءة راجعة.
- **يحتاج موافقة:** الاستيراد الفعلي فقط؛ المعاينة قراءة فقط.
- **المخرج:** تقرير معاينة (ملف، profile، تحليل، أرصدة، exact/possible، خطة استيراد) ثم نتيجة التنفيذ والتحقق.
- **الحدود:** لا تسوية ولا حذف ولا تعديل؛ الصيغ المدعومة CSV وXLSX وXLS (XLS عبر xlrd المثبّت)؛ OFX/QFX/CAMT.053 غير مدعومة بعد. التفاصيل في `statement-import.md`.
